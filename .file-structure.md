# `.file-structure.md`: how this repo is laid out, and the rules for adding to it

**Who this is for:** anyone, human or AI, who adds to or edits this repo. Read it before you
create a file. If you change the layout, update this file in the same commit.

**The one-line rule:** *every fact lives in exactly one place, in a folder named for what it is,
in a file named for what it covers, with a date stamp telling you how fresh it is.*

---

## 1. The tree

```
/                                   ← repo root (PUBLIC on GitHub)
├── README.md                       Front door for humans: what this is, where to start
├── CLAUDE.md                       Front door for AIs: read order + hard rules
├── memory.md                       Running notes for AIs: decisions, problems & solutions
├── .file-structure.md              THIS FILE: layout + conventions
├── .gitignore                      Keeps the private stuff below out of git
│
├── .update-the-repo-info/          How to refresh the data later (a year from now, whenever)
│   ├── README.md                   The playbook: who / what / when / where / why / how
│   ├── sources.md                  Every data source, what it's good for, how to query it
│   ├── checklist.md                Step-by-step refresh procedure, in order
│   ├── changelog.md                One entry per refresh (newest on top)
│   └── scripts/                    Repeatable pulls (e.g. refresh-nhtsa.sh)
│
├── templates/                      Copy these when making a new doc. Don't freelance a format.
│   ├── item-doc.md                 Explainer doc (a maintenance item, a known issue, …)
│   └── folder-readme.md            Index page for a folder
│
├── vehicle/                        What the car IS: specs, fluids, VIN decoding, warranty
├── maintenance/                    One doc per service item + README index/schedule/cost table
├── known-issues/                   One doc per common failure + README ranked index
├── recalls/                        Recall list + how to check a VIN
├── tires/                          Fitments, categories, run-flat question, model comparison, buying
├── where-to-service/               Dealer vs independent vs DIY, labor rates, upsells, quote audit
│
├── official-docs/                  Primary documents (PDFs), never edited
│   ├── README.md                   Index: title, publisher, source URL, date retrieved, SHA-256
│   ├── bmw/                        BMW-published documents
│   └── nhtsa/                      U.S. government documents
├── data/                           Raw machine-readable pulls (JSON/CSV). Regenerate, don't hand-edit
│   ├── README.md                   What each file is + the exact command that produced it
│   └── nhtsa/
│
├── .links-i-found-for-starting     Owner's starter list of source links (public-safe; folded into .update-the-repo-info/sources.md)
│
├── .memory                         🔒 PRIVATE, gitignored: the owner's VIN decode + profile
├── private/                        🔒 PRIVATE, gitignored: owner's location, shops, quotes, audits
└── service-records/                🔒 PRIVATE, gitignored: raw dealer paperwork / inspection exports (as-received)
```

### What goes where (decision table)

| If the thing you're adding is… | It goes in | Example |
|---|---|---|
| A service you *schedule* (has an interval) | `maintenance/<item>.md` | `maintenance/brake-fluid.md` |
| Something that *breaks* (not scheduled) | `known-issues/<issue>.md` | `known-issues/valve-cover-gasket.md` |
| A safety recall | a row in `recalls/README.md` | 26V056000 starter |
| A spec, capacity, part number, warranty term | `vehicle/` | `vehicle/specs-and-fluids.md` |
| Anything about tires/wheels | `tires/` | `tires/run-flat-vs-non-run-flat.md` |
| Advice about *who* should do the work / pricing models | `where-to-service/` | `where-to-service/upsells.md` |
| A PDF or primary document | `official-docs/<publisher>/` + a row in its README | warranty booklet |
| Raw data from an API | `data/<source>/` + the command in `data/README.md` | NHTSA complaints JSON |
| How to refresh any of the above | `.update-the-repo-info/` | `sources.md` |
| **Anything about one specific owner, car, location, or shop** | 🔒 `.memory` or `private/` | VIN, ZIP code, our audit of a quote |
| Raw paperwork exactly as a shop sent it (PDF, JSON export, photos) | 🔒 `service-records/` named `YYYY-MM-DD_<shop>_<what>.<ext>` | `2026-10-02_<dealer>_mpi.json` |

If nothing fits, **don't** make a junk-drawer folder (`misc/`, `notes/`, `other/`). Add a new
topic folder, give it a `README.md` from `templates/folder-readme.md`, and add it to the tree
above.

## 2. Public vs private: the most important rule

This repo is **public**. Its job is to be a general knowledge base for the BMW G20 330i /
330i xDrive that anyone (a Redditor, an AI) can read.

- **Public files are general.** Prices are national ranges, not one shop's quote. Advice is per
  *situation* ("if you live in a snow state…"), not per person.
- **Private things go in `.memory`, `private/`, or `service-records/` only.** All three are in `.gitignore`. That means:
  full VINs, names, addresses/ZIP codes, the owner's dealer or shop, quotes and invoices,
  mileage logs, photos of the car, account numbers.
- **Before every commit:** `git status` must not list `.memory` or anything under `private/` or `service-records/`.
  If it does, stop and fix `.gitignore`.
- An example VIN in a public doc is fine **only** if it's clearly fake
  (`WBA00000000000000`) or a partial (the last 6–7 characters, e.g. `…A12345`, still identify a car, so don't).

## 3. Conventions every doc follows

### 3a. The date stamp (required, top right, first line of the file)

```html
<p align="right"><i>Last updated on <b>Oct--02--2026</b></i></p>
```

- Format is **`Mmm--DD--YYYY`** (3-letter month, two dashes, 2-digit day, two dashes, 4-digit
  year), the owner's chosen format. Use it exactly, everywhere.
- GitHub renders `align="right"`, so it shows top-right.
- Bump it **only** when you change facts in that file, not for typo fixes. Its whole purpose is
  answering "how much can I trust this today?"

### 3b. File and folder names
- `lowercase-kebab-case.md`. No spaces, no capitals, no dates in filenames (the date is in the
  stamp; git has the history).
- Name for **what it covers**, not what it's for: `spark-plugs.md`, not `when-to-change-plugs.md`.
- Every folder has a `README.md` index linking to everything in it.

### 3c. Explainer docs (maintenance items, known issues) use `templates/item-doc.md`
Fixed section order, so a reader (or an AI) always knows where to look:

1. Date stamp
2. `# Title` + one "Applies to" line
3. **TL;DR / ELI5**: one plain-English paragraph a non-car-person understands
4. **How much it actually matters**: `x/5` rating + one-sentence why
5. **What the forums say**: the "skip it" camp, the "do it now" camp, where consensus lands
6. **Cost & time**: table with DIY / Independent shop / BMW dealer price **and** time
7. **When to do it**: BMW's interval vs the enthusiast interval
8. **DIY verdict**: Dead simple / Doable with tools / Leave it to a shop, plus what you need
9. **Watch out for**: upsells, gotchas, warranty angles
10. **Sources**: links, each with the date it was checked

### 3d. Prices
- Always **USD, national general ranges**, labeled with the year they were checked
  (e.g. "2026 USD"). Never one shop's number in a public file.
- Always three tiers in this order: **DIY (parts) → Independent shop → BMW dealer**.
- Always include **time**: DIY time (first-timer / experienced) and shop labor hours or "while
  you wait / drop off".

### 3e. Facts and sources
- Anything numeric (capacity, interval, torque, part number, price) gets a source link.
- Primary sources (BMW docs, NHTSA, ZF) beat forums. Forums are for *opinion and experience*;
  label them as such.
- If you couldn't verify something, say so inline: `⚠️ unverified`.
- Don't paste copyrighted text. Summarize and link. Quotes under ~15 words, attributed.

### 3f. Ratings scale (used everywhere)
| Rating | Meaning |
|---|---|
| 5/5 | Skip it and you risk an expensive or dangerous failure |
| 4/5 | Important; don't stretch it far |
| 3/5 | Worth doing on schedule, low drama if a little late |
| 2/5 | Nice to have; fine to do when convenient |
| 1/5 | Cosmetic, optional, or mostly an upsell |

### 3g. Language
- Write for a smart non-mechanic. Define jargon once (e.g. "CBS (Condition Based Service, the
  car's own maintenance reminders)").
- Lead with the answer. Tables over paragraphs for comparisons.

## 4. Using this as a template for another car or project

Copy the skeleton (root files, `.update-the-repo-info/`, `templates/`, `official-docs/`,
`data/`, `.gitignore`, `.memory`, `private/`) and rename the topic folders to fit. Keep sections
2 and 3 as they are: the public/private split and the doc conventions are what keep it orderly.
